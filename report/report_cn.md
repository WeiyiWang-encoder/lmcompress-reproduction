# 摘要

本报告记录了对 Li 等人发表于 *Nature Machine Intelligence* **7**:794–799 (2025) 的
LMCompress 大模型无损压缩方法的完整复现。全部压缩逻辑——算术编码器、测量引擎、
四种模态的加载器以及三个模型的封装——均为独立编写。作者发布的代码（Code Ocean
capsule）仅作为**参照对象**、**预训练权重来源**，以及在第五章中作为**被观察的可执行
对象**使用；本复现自身的代码路径从未调用其压缩例程。

复现结果**部分成功**，而成功与失败的模式本身就是主要结论。文本模态与论文的差距为
**0.04 个百分点**；音频模态复现成功——我们独立编写的算术编码器对 82 220 字节载荷
输出 130 383 bit，而参考实现对同一载荷报告 16 399.95 字节，两者相差 **0.6 %**。
但在图像与视频模态，模型报告的"压缩率"**并非针对源数据的码率**：官方管线在编码前
把每幅图像归约为 32×32、512 色的 token 网格，而分母统计的是全分辨率源图像样本数。
我们通过**穷举证明**该预处理**不是单射**——256 个可能的 8 bit 通道值只映射到
**48** 个不同 token id，存在 **585** 个碰撞值对——因此不存在能够恢复源值的解码器。
论文为"逐通道独立压缩"给出的理由（"因为 iGPT 的 token 是灰度值"）**与事实不符**：
512 个调色板条目全部是 RGB 三元组，**没有任何一个是灰度**。

我们还审计了论文的文本微调结论。**运行作者自己未修改的脚本**，发布的 LoRA 适配器
使 MeDAL 的压缩率在上下文 8192 下**变差 0.5901 个百分点**；我们的独立端口在上下文
4096 下测得同方向（+0.312 pp）。适配器自身的训练日志显示评测损失在**第 1020 步
（约 2 个 epoch）达到最小**，此后退化——发布的 checkpoint 是第 5120 步。

四类经典基线全部复现，其中视频基线吻合最好（最大偏差 1.17 pp，FFV1 与 zstd 在
0.01 pp 以内）。由于本项目中有**三项自己提出的结论后来被自己的验证工具推翻**，
本报告明确保留全部撤回记录，并附上可机器校验的检查器，以便读者重新推导数字而非
相信数字。

# 第一章 引言

## 1.1 研究动机

无损压缩应用于必须逐比特精确还原原始数据的场合：法律文书、医疗记录、可执行代码、
密码学材料与档案级多媒体。它的理论极限由香农信源编码定理确定。对于概率质量函数为
$p(x)$ 的离散信源 $X$，任何唯一可译码的平均码长都不能低于熵

$$H(X) = -\sum_x p(x)\log_2 p(x),$$

而对于有记忆的信源，起作用的极限是熵率

$$\bar H = \lim_{n\to\infty} H\left(X_n \mid X_1,\dots,X_{n-1}\right).$$

这个式子包含了全部设计问题。若条件分布 $P(x_t \mid x_{<t})$ 已知，则码长

$$L(x_{1:n}) \approx -\log_2 P(x_{1:n}) = -\sum_{t=1}^{n}\log_2 P(x_t \mid x_{<t})$$

即可达到下界。因此压缩自然地分解为两个可分离的部件：估计条件分布的**预测器**，
以及把该分布映射为唯一可译比特串的**编码器**。这一分离正是预测器研究得以独立于
编码器研究的原因。

LMCompress 用大型预训练模型作为预测器来实现这一分解。其前提是：一个**理解**了某
领域的模型会给该领域真实产生的数据更高的概率，因此编码它需要更少的比特。

## 1.2 本项目的范围

Capstone 任务的要求是**仅做复现**：重新实现并验证已发表的方法，而非提出新的压缩器。
因此本报告不提出新的压缩算法，而是回答四个问题：

1. 该管线能否从零重新实现，并复现论文报告的数字？
2. 复现出的管线是否如论文所称是**无损**的，即能否精确还原原始数据？
3. 复现与论文不一致之处，原因是什么？
4. 同一套评测协议对论文自身的微调结论意味着什么？

答案依次是：文本与音频**可以**；图像与视频按当前评测方式**不可以**；第三、四个问题
用**可测量的机制**而非推测来回答，且每一机制都可被独立检验。

## 1.3 主要贡献

- 完整的 LMCompress 四模态净室实现，包括自写的整数区间编码器，其正确性通过穷举
  往返测试建立。
- 对四种模态系统性复现，同时对照论文数字与作者的参考实现，并在每种模态上复现
  经典基线作为**对照**。
- 穷举证明官方图像/视频预处理**非单射**，并**修正论文关于 iGPT token 的技术前提**。
- 用作者自己未修改的 harness 复现文本微调实验，**测得与论文相反的方向**，并分析
  发布 checkpoint 自身的训练日志。
- 可验证的研究记录：本项目有三项自己的中间结论被推翻，全部连同撤回理由一并记录，
  并附机器可校验的 harness。

# 第二章 背景

## 2.1 从手工预测器到大模型

神经网络之前的无损压缩沿两条轴发展。Lempel–Ziv 家族（最广为使用的实现是
LZ77 加 Huffman 编码的 DEFLATE）在滑动窗口中寻找重复子串并对匹配记号做熵编码。
上下文混合方法（LOEMA、PPM 及其变体、PAQ）用变阶马尔可夫模型估计下一符号概率，
彼此主要在阶数加权方式与 escape 概率分配上不同。

对本报告而言关键的概念性一步是：在链式法则下，**更好的概率模型直接就是更短的码**，
无需改动编码器。DeepZip（2019）把 RNN 与算术编码耦合，并实验观察到平均码长与交叉熵
损失一致——这正是"训练损失与压缩性能是同一量"的陈述。Izacard 等人（2018）用
Transformer 替代 RNN，确立了纯神经预测器具有竞争力。LLMZip 随后表明，现成的预训练
大模型无需任务特定训练即可迁移为压缩先验。

LMCompress 把这一思路从文本扩展到四种模态，使用三个模型族：文本用 Llama-3-8B，
音频用自行训练的字节级 bGPT，图像与视频用 ImageGPT（iGPT）。流程统一为
「数据 → token → 自回归条件分布 → 算术编码」，但**分词方式因模态而异**——
第八章将说明，问题正出在这里。

## 2.2 熵编码

实践中有两类编码器占主导。Huffman 编码对已知有限分布给出最优前缀码，但无法为符号
分配少于一个比特。算术编码通过把整条消息映射到 $[0,1)$ 的一个子区间而消除该下限，
码长可任意接近 $-\log_2 P(x_{1:n})$；工程实现或采用二值算术编码，或采用定点区间的
**整数区间编码**——本报告使用的是后者。

## 2.3 算术编码的误差界，以及为什么编码器几乎从不是瓶颈

算术编码把消息 $x_{1:n}$ 表示为一个长度等于 $P(x_{1:n})=\prod_t q_t(\omega_t)$ 的
子区间。区间内任意一点即可确定消息，因此所需比特数为

$$\ell(x_{1:n}) = \left\lceil -\log_2 P(x_{1:n}) \right\rceil + 1 \le -\sum_t \log_2 q_t(\omega_t) + 2.$$

**全部开销只有两个比特**，这正是为什么这类压缩结果本质上是对**预测器**的陈述。
区间编码器以有限精度实现同一下界：在 $2^{32}$ 标度下，当前宽度为 $w$、符号 $s$ 的
累积边界为 $\mathrm{lo}_s,\mathrm{hi}_s$ 时，区间更新为

$$\mathrm{low} \leftarrow \mathrm{low} + \left\lfloor \frac{w\,\mathrm{lo}_s}{2^{32}}\right\rfloor,\qquad
\mathrm{high} \leftarrow \mathrm{low} + \left\lfloor \frac{w\,\mathrm{hi}_s}{2^{32}}\right\rfloor.$$

支配实现的设计后果是**精度**。若某分布给某符号的概率低于 $2^{-p}$，则量化区间宽度
为 1，编码器无法在不做更强重归一化、或不预留最小宽度的前提下表示该符号。本工作为
每个符号预留 $2^{32}/2^{20}$，即把单符号最坏代价限制在 20 bit。第五章记录了若无此
预留会发生的**静默错误**。

## 2.4 字节的可预测性，与自相关的算术

对面向字节的模态，有必要明确预测器能利用与不能利用什么，因为这解释了第八章中一个
初看令人意外的测量。对 8 bit PCM 音频，起支配作用的是"给定紧邻前驱时一个字节的熵"。
一个平凡的一阶模型——预测下一字节等于当前字节——在我们的测试片段上达到
**23.74 %** 的 argmax 准确率，这界定了短程自相关单独可带来的增益。若模型改为预测
**若干位置之后**、处于固定栅格偏移的字节，那是利用周期性结构而非顺序结构，其准确率
是另一个量。定量区分这两个任务，正是使我们判定 bGPT checkpoint 实际在做什么的依据
（见第九章）。

# 第三章 被复现的方法

## 3.1 流程

四种模态都经历相同的三个阶段：

1. **分词**。把原始数据转换为模型可处理的 token 序列。文本用模型自带 BPE 分词器；
   音频把字节填入固定大小的 patch；图像与视频使用 ImageGPT 的彩色量化处理器。
2. **预测**。运行自回归模型，在每个位置 $t$ 得到下一个 token 的分布 $q_t$。
3. **编码**。用算术编码把真实 token 序列对 $q_t$ 编码。报告的码长为
   $\sum_t -\log_2 q_t(\omega_t)$。

## 3.2 模型与论文报告的工作点

| 模态 | 模型 | 分词 | 报告设置 |
|---|---|---|---|
| 文本 | Llama-3-8B ± LoRA | BPE（Llama-3 词表） | LMCompress\* = 不微调；LMCompress = LoRA 微调（rank 8, α=32） |
| 音频 | bGPT（字节级） | 字节 → 16 字节 patch | 预印本称 2048 字节 patch；随附 capsule 使用上下文 8160 |
| 图像 | iGPT-small | 32×32、512 色调色板 | 1024 像素分段，逐通道独立编码 |
| 视频 | iGPT-small（逐帧） | 同图像，逐帧 | 帧独立编码；**不使用**帧间信息 |

## 4.3 指标口径的精确定义

本项目反复出现的错误来源——我们随后会论证，也是图像与视频评测的问题所在——是
**未声明的分母**。因此在此固定口径。

> **定义**。对于长度为 $N$ 的载荷，对模型分布 $q_t$ 编码得到的**报告码长**为
> $C = \sum_{t=1}^{N} -\log_2 q_t(\omega_t)$ bit，在模型自身的 float32 概率上求值。
> **压缩率**为 $C/8N$ 的百分比形式，**比值**为 $N/(C/8)$。

两个推论很重要。第一，$C$ 在任何编码器量化**之前**计算：量化后的 CDF 只影响算术
编码的字节流，实现中单独记为 `ac_bits` 并作为一致性检查报告，**从不作为结果**。
第二，分母 $N$ 是**载荷符号数**，本报告中的每个率都标明其分母。

# 第五章 实现

## 5.1 区间编码器，以及我们在其中发现的数值失效

我们的编码器用定点整数算术细分单位区间。对符号的累积边界 $\mathrm{lo},\mathrm{hi}$
（$2^{32}$ 标度），当前区间宽度 $w$，新区间为

$$\mathrm{low}' = \mathrm{low} + \left\lfloor \frac{w\cdot \mathrm{lo}}{2^{32}}\right\rfloor,\qquad
\mathrm{high}' = \mathrm{low} + \left\lfloor \frac{w\cdot \mathrm{hi}}{2^{32}}\right\rfloor.$$

第二项的下取整是隐患。若某符号被量化为宽度 1 的区间而 $w < 2^{32}$，计算出的增量
为 0，于是 $\mathrm{high}' \le \mathrm{low}'$：**区间塌陷**，编码器输出一段解码为
**错误**符号却报告成功的码流。我们用一个真实的模型输出触发了它：某个分布中真符号的
$p = 9.06\times10^{-11}$，被分配到宽度为 1 的区间。该失效是**静默的**——我们的第一版
实现产出了看起来合理的输出。

修法分两部分：为每个符号预留最小宽度（`min_interval_width()`，$2^{32}/2^{20}$），
并加入断言，使塌陷永不再静默。

**一个我们弄错并已更正的论证。** 早期版本的项目笔记声称该预留无害，理由是"20 bit
高于字节字母表的 8 bits/byte 上限"。该论证**无效**：拥有 256 个符号并不限制真字节的
surprisal，因此标定不良的模型可以给出 $p < 2^{-20}$，此时下取整确实改变了编码器所用
的分布。该预留仍然无害，但理由不同也更简单，即第四章所述：**报告率从不取自编码器
量化后的概率**。无效论证与其更正都被保留在源码 docstring 中，以防再次引入。

## 5.2 文本：分词、窗口，以及一个目标切片缺陷

文本用 Llama-3-8B 的 BPE 分词器对模型的下一 token 分布编码，滚动窗口 4096 token。
长文档按带重叠的窗口序列处理。

**我们在自己代码中发现的缺陷。** 早期版本对每个 token 都用**其前驱**的分布打分：
logits 切片与目标切片相差一个位置，而一个"丢弃第一个预测"的补偿既掩盖了错误，又
静默丢弃每篇文档的最后一个 token。它之所以被发现，仅仅是因为一位审阅者反对我们为
缺失 token 给出的**解释**——我们把它归因于因果模型无法预测自己的最后一个 token，
而这是**错的**，因为因果语言模型正是从倒数第二个位置预测最后一个 token。

更正后的实现把被打分区间连同前后各一个上下文 token 一起送入（二者都不计分），
并**逐 token 断言**目标必须等于其应等于的文档 token。任何位数的滞后都会立即报错。
该更正把基座模型的率从 9.0333 % 移到 **9.0410 %**——即**更接近**论文的 9.08 %——
LoRA 臂从 9.3459 % 移到 9.3529 %。

## 5.3 音频：字节 patch 与索引记账

音频按字节序列处理。bGPT 消费固定 16 字节的 patch，并由于其掩码被内部左移，
每个 patch 返回 **17** 个 slot 预测：16 个给本 patch 自己的字节，另有 1 个承载对下一个
patch 首字节的预测。其后果——我们在第九章建立并审计——是：预测载荷位置 $k$ 的扁平
logits 行号为

$$r(k) = 17\left\lfloor \frac{k}{16}\right\rfloor + \left(k \bmod 16\right),$$

而**不是**朴素的 $16+k$。把这个弄错——两者之差每过一个 patch 增加一——正是我们最严重
那次撤回声明的根源。

窗口被精确铺满载荷；在参考实现做不到的情形下，末尾短窗口被补齐到 patch 大小的整数倍，
以使每个载荷字节恰好被编码一次。这属于**移植行为**而非对参考行为的复现，凡可能影响
比较之处我们都会标注。

## 5.4 图像与视频

图像用 iGPT-small 编码。由于官方路径逐通道处理，我们的"单元"是下采样 patch 的一个
通道，账目遵循第八章所述的官方口径。视频逐帧复用图像路径，与论文规定完全一致：
每帧独立编码，不使用任何帧间信息。

驱动官方代码作为参照需要两个实现细节。第一，ImageGPT 处理器必须在**类级别**打桩；
实例级打桩会静默失败，因为模型参数会被 `_retrieve_model_params` 重新物化。第二，
官方图像日志每 100 个 chunk 才打印一次，因此**它自己打印的总数是过期的**，真实总数
必须外部累加。

# 第八章 审计：图像与视频评测管线

## 8.1 该处理器是固定预处理，不是压缩方法

ImageGPT 处理器从 checkpoint 一次性载入并原样应用。其配置（`preprocessor_config.json`）
明确写道：512 个 RGB 三元组聚类中心、`do_color_quantize: true`、`do_resize: true`、
`size: {height: 32, width: 32}`、`image_processor_type: "ImageGPTImageProcessor"`。

由此可得三个性质，它们回答了该部件"是什么"：

1. **它在压缩过程中不被训练。** 512 个聚类中心是随 checkpoint 发布的固定查找表；
   图像路径中没有任何代码拟合或更新它们。
2. **它是模型自带的分词器，继承自 iGPT。** iGPT 是关于离散颜色 token 的自回归模型；
   调色板就是它的词表。没有它就无法使用该模型。
3. **压缩方法是 Transformer 加算术编码。** 处理器提供分词，码长来自模型在所得
   token id 上的预测分布。

论文与这一读法一致：§2.1 把该步骤描述为"把二维视觉数据变换为一维像素序列"，
即**分词**，而从未称之为方法本身。论文**没有**描述的是——正文与补充材料中均无——
该分词器会**量化颜色**并**缩放到 32×32**。文中完全没有提到颜色聚类、512 色调色板、
32×32 缩放或 9 bit token。该行为只存在于代码中，`language_model.py` 在调用处理器前
设置了 `do_color_quantize = True`。

## 8.2 论文给出的理由与事实不符

论文为逐通道独立编码给出的理由是：

> "Because the tokens of iGPT are greyscale values, we regard an image as three
> greyscale images, one for each RGB channel … During decompression, each channel is
> decompressed independently, and the three channels are then merged to reconstruct
> the original image."

我们对照 checkpoint 自身的调色板核查了这一点，结论是**该前提为假**。512 个聚类中心中：

| 检查 | 结果 |
|---|---|
| `clusters` 的形状 | (512, 3)——512 个 RGB 三元组 |
| 恰好是灰度（R=G=B）的条目 | **0 / 512** |
| 近灰度（最大通道偏差 < 0.05） | 61 / 512 |

**token 是颜色，不是灰度级。** RGB 空间的灰度对角线——集合 $\{(v,v,v)\}$——与该调色板
只有稀疏交集，而这种稀疏性正是逐通道管线有损的原因，见下节。

## 8.3 穷举证明该路径非单射

loader 逐通道切分图像，因此 `language_model.compress` 收到形状为 $(32,32,1)$ 的张量。
由于其最后一维为 1，代码走 `np.repeat(..., 3, axis=2)` 分支，并以 $(32,32,3)$ 调用
处理器——即由**单个** 8 bit 通道值 $v$ 构成的 $(v,v,v)$。处理器把该三元组映射到 512 个
颜色 token 之一，而编码器**只传输所得的 token id**。

因此定义域恰好是 256 个值，这使得该问题**可判定**——用穷举而非论证。注意一个朴素的
基数论证——"每像素 24 bit 降为 9 bit"——在此**无效**，因为定义域确实是 256 而值域是
512；我们自己的早先版本用过该论证，一位审阅者正确地驳回了它。

| 量 | 值 |
|---|---|
| 定义域大小（8 bit 通道值） | 256 |
| **像大小（不同 token id）** | **48** |
| 单射 | **False** |
| 碰撞值对 | **585** |
| 最大碰撞类 | token 391 ← 7 个值（78…84） |

可直接从发布的 JSON 复现的例子：

```
token  71  <-  灰度值 [0, 1, 2, 3]
token  59  <-  灰度值 [8, 9, 10, 11]
token 391  <-  灰度值 [78, ..., 84]
```

两项进一步检查排除了显然的反驳。第一，碰撞不是合成常量输入的假象：在**真实 patch**
（patch #116）上，110 个不同源值塌缩为 32 个 token，其中 29 个 token id 接收多个源值。
第二，损失不只是舍入扰动：它是定义在管线**实际使用的精确输入字母表**上的多对一映射。

**推论。** 存在不同值 $a \neq b$ 使 $\mathrm{token}(a,a,a) = \mathrm{token}(b,b,b)$。
编码器只发出该 token id，且不附带任何残差或边信息。因此**不存在能够恢复源值的解码器**，
该管线**对 token 网格无损、对图像有损**。这直接与论文"三个通道随后被合并以重建原始
图像"的表述矛盾。

**分母不是问题所在。** 值得明确说明，因为这也是我们自己最初（且错误）的诊断：
分母恰好统计了管线实际处理的样本，内部是自洽的。缺陷在预处理，不在比值。

## 8.4 一条独立的第二证据

loader 在把通道切分为 1 024 像素块时使用整除，每通道丢弃 **524** 个样本——共 **1 572**
个，占源的 0.027 %。这是该路径不保持源的**第二条独立证据**，我们把它作为证据而非对
率的实质性修正提出。

## 8.5 视频继承全部结论

视频使用相同的 loader、相同的处理器与相同的代码路径，逐帧处理且不使用帧间信息——
与 §2.2.1 完全一致。每帧缩减为 8 640 倍，大于图像情形，而 §7.5 的表显示精确重建需要
约 73 % 的帧字节。因此模型行正确的描述是「**一个 32×32、512 色代理对象的码长**」，
不应与视频编解码器的率当作测量同一对象来比较。

## 8.6 本复现**不**主张什么

- 我们不主张图像或视频的**分母**有错。它是自洽的。
- 我们不主张论文的图像或视频率是伪造的。它们正是发布代码在发布口径下产生的值。
- 我们不主张 32×32 缩略图是无用的表示——只主张针对它的率不是针对图像的率。
- 我们不主张这些模型无能。相反，文本模型复现到 0.04 pp，音频模型优于所有被测经典
  编解码器。

# 第九章 bGPT 索引推导与因果性检验

音频模态是本复现犯错最严重之处，因此也是验证最详尽之处。我们在此完整给出推导，
因为错误的更正依赖于把它完全弄对。

## 9.1 为什么一个 patch 行承载 17 个预测而非 16 个

bGPT 以 16 字节的 patch 消费字节流。其 `forward` 把 patch 掩码的首元素置零并左移掩码
后再选择 patch，因此返回的 logits 从 patch 1 开始，且每个返回的 patch 行含 **17** 个
slot 预测：16 个给自身的字节，另 1 个承载对下一 patch 首字节的预测。最后一个 patch 行
没有后继可贡献，被调用方丢弃。

参考实现的切片是

```python
logits = logits[:-1, :-1, :]                 # (510, 16, 257) -> 8160 行
logits = logits.reshape(1, -1, 257)
input_ids = input_ids[:, PATCH_SIZE:-PATCH_SIZE]   # payload[0:8160]
```

因此它的行集是 **patch 主序、每行去掉最后一个 slot**：行 $k$ 对应
(patch $p$, slot $j$)，其中 $k = 16p+j$。

## 9.2 载荷位置对应的行号

logits 的展平使用步长 **17** 而非 16，因为每个 patch 在切片前贡献 17 行。因此承载
载荷位置 $k = 16p+j$ 预测的扁平行是

$$r(k) = 17p + j = 17\left\lfloor \frac{k}{16}\right\rfloor + \left(k \bmod 16\right),$$

而朴素写法 $16+k$ 只在 $p=0$ 时与之相同。两者在 $k<16$ 时相等，此后**每过一个 patch
相差一**，到位置 $k$ 时累计相差 $p$。用 $16+k$ 就等于把每一行拿去与偏离它约 $k/16$
个位置的字节打分。

这正是 §11 中那次撤回声明的根源：我们"诚实的 next-byte"探针用了 $16+k$，
而那根本不是诚实的行号。

## 9.3 参考实现实际配对了什么（实测）

有了正确索引，问题变成经验性的：某一行最自信的是哪个字节？我们扫描候选偏移 $L$，
对 $\mathrm{grid}[16p+j+L]$ 求该行所赋概率的平均值：

| 偏移 $L$ | 平均概率 | argmax 命中率 (%) |
|---|---|---|
| 1（紧随其后的字节） | 0.0804 | 7.26 |
| 8 | 0.1448 | 15.81 |
| 15 | 0.2199 | 26.07 |
| **16** | **0.3052** | **37.18** |
| 17 | 0.1923 | 20.94 |

该行对偏移 **16** 最自信，而参考实现恰好把它与那个字节配对：行 $k = 16p+j$ 对应的
`payload[k]` 是 $\mathrm{grid}[16+k] = \mathrm{grid}[16(p+1)+j]$，即**一个 patch 之后
的同一 slot 索引**。所以参考实现的配对对该 checkpoint 而言是自洽的。我们此前称其为
"错位"的说法**是错的**。

## 9.4 因果性检验：自洽还不够

一个码要能**无损解码**，仅自洽不足够：赋予字节 $k$ 的分数**不得依赖 $k$ 之后的任何
字节**，因为解码器尚未见过它们。我们通过扰动目标之后的字节并重跑模型直接检验：

| 扰动 | 全词表 $\max|\Delta \log p|$ | 解释 |
|---|---|---|
| 目标**之后**的字节 | 0.000000e+00 | 因果：分数不变 |
| 目标**之前**的字节（对照） | 9.436880 | 探针有效 |

该方案是合法的因果码，参考实现报告的数值对该 checkpoint 所实现的方案而言是**真实的
码长**——并由算术编码器确实输出了这些字节独立确认。

## 9.5 对复现的意义

由此可得两点。第一，我们端口的音频数字可信，且与一次独立参考运行在**实际字节流**上
吻合到 0.6 %。第二，该 checkpoint 的编码方案**不是**朴素的 next-byte 编码：它对
16 个位置之后的那个字节最自信。这是关于方法设计的陈述而非关于其有效性的陈述，
但它确实意味着任何写作都应准确描述该方案——读者若把它与常规 next-byte 编码器比较，
比较的是两个不同任务。

# 第十章 微调结论

## 10.1 论文报告什么，发布物又做什么

正式发表的 SI Table 6 报告 MeDAL 在未微调时（LMCompress\*）为 9.08 %，LoRA 微调后
（LMCompress）为 9.06 %：增益 **0.02 pp**，相对 0.2 %。在 Pile of Law 语料上同一配方
报告 5.86 → 4.90 %，相对提升 **16 %**。论文给出的划分是 64 MB 训练 / 16 MB 验证 /
其余测试，LoRA rank 8、α = 32、batch size 1 且每 8 步累积梯度、10 个 epoch、
学习率 $10^{-4}$、前 10 % 为 warm-up、基座以 8 bit 载入并以 bfloat16 训练。

我们用两种独立方式检验该结论。

**检验一：我们的端口。** 三个 MeDAL 文件，窗口与代码路径相同，只有 `lora_path` 不同：
9.0410 %（基座）对 9.3529 %（LoRA），惩罚 +0.312 pp，三个文件一致。

**检验二：作者自己未修改的脚本。** 为排除我们 harness 的缺陷，我们直接运行参考脚本
本身，**未做任何修改**，只改 `lora_path`：

| 臂 | 官方 ratio | 率 (%) |
|---|---|---|
| 基座，无适配器 | 11.204097 | 8.9253 |
| + 作者发布的 LoRA 适配器 | 10.509252 | 9.5154 |
| 差 | −0.694845 | **+0.5901（更差）** |

由此得两个结论。第一，**基座上两个独立实现相差 0.0622 pp**——端口是忠实的。第二，
作者自己的代码、跑在作者自己的适配器上，复现出与其发表表格**相反的方向**。
因此分歧在**代码与论文之间**，而不在复现与代码之间。

## 10.2 原因：发布的 checkpoint 正是过拟合的那一个

适配器自身的 `trainer_state.json` 记录了评测轨迹：

| 步数 | Epoch | Eval loss |
|---|---|---|
| 20 | 0.04 | 2.7491 |
| **1020** | **≈2.0** | **2.4708（最优）** |
| 5120 | 10.0 | **2.6728（退化 8.2 %）** |

发布的适配器是第 **5120** 步的 checkpoint——已越过最小值八个 epoch。一个评测损失上升
了 8.2 % 的模型，预期会更差地建模其领域，而这正是两个 harness 测到的。这也意味着
论文按其自身描述执行到 10 个 epoch 的配方，并不是产生其报告数值的东西——除非所用的
是不同于所发布的另一个 checkpoint。

## 10.3 排除我们自己的加载路径

我们的端口在评测前把适配器合并进基座（`merge_and_unload()`），这是一个潜在假象来源：
把低秩增量折叠进量化权重可能有损，甚至静默无效。我们用三种方式检验。

**第一，两臂确实不同。** 若合并丢弃了适配器，两臂会执行完全相同的前向并产生完全
相同的比特数。它们相差 2 185.24 bit / 19 338 token。

**第二，合并保真度实测。** 在真实 MeDAL 载荷的前 4 096 个 token 上，**不做任何量化**：

| 臂 | bits/token |
|---|---|
| 基座，无适配器 | 2.565796 |
| + 适配器，**未合并**（忠实路径） | 2.772864 |
| + 适配器，**已合并**（我们的路径） | 2.776077 |
| 适配器效应，未合并 | +0.207068 |
| 适配器效应，已合并 | +0.210281 |
| 合并失真 | +0.003213（惩罚的 2.84 %） |

**适配器在忠实的未合并路径上使压缩变差 +0.207 bits/token，而合并只增加 0.003。**
因此**合并不可能是让适配器显得差的原因**——不用它把惩罚更大。

**第三，一个残留怪现象。** 在一个短的通用临床句子上，合并后的模型与基座**逐比特相同**：
bf16 的折叠把很小的增量完全舍入掉了。这不影响上述数字，但说明合并保真度依赖输入与
dtype，合并路径不应在未做此检验前被假定为精确。**首选评测方式是不要合并。**

## 10.4 必须随该结论一起声明的混淆项

惩罚是在上下文 **4096** 下测得的。论文自己的 SI Table 9 报告 MeDAL 在上下文
8192/6144/4096 下为 9.06/9.16/9.36——跨度约 **0.3 pp**，与惩罚**同量级**。
因此，测得的惩罚中有多少归因于适配器、多少归因于更短的上下文，**目前尚未确定**。

已经确定的是**方向**：两个独立 harness、在两个不同上下文长度下，都测得适配器有害。
尚待确定的是**归因**，这需要一次上下文 8192 的配对运行。

## 10.5 与文献综述框架的关系

随本报告附上的文献综述把 LMCompress 定位在"大模型作为压缩先验"这条线索（LLMZip 及其
前驱）从文本扩展到四种模态的节点上。微调结论在这一框架下恰有意义：论文自身的框架是
域适配锐化了先验、因而缩短了码长，Pile of Law 的数字强烈支持这一点（相对 16 %）。
而在 MeDAL 上，已发表的增益是 0.02 pp——已经在噪声里——且发布物出现退化。诚实的总结
是：域适配在一个域上效果显著，在另一个域上完全无效，且后者的发布 checkpoint 训练过度。

# 第十一章 撤回与更正

本项目有三项自己的结论后来被推翻，其中两次是被专门为检验它们而写的工具推翻。
我们记录它们，是因为一份隐藏自己错误的复现报告，其价值低于一份记录错误的报告；
也因为八项撤回中有四项共享一个值得命名的共同根源。

| 曾主张 | 状态 | 根源与更正 |
|---|---|---|
| 参考实现的音频打分错位 16 位，夸大 6.29× | **撤回** | 我们的探针把扁平 logits 索引为 $16+k$，但一个 patch 行承载 **17** 个 slot 预测；正确行号是 $17\lfloor k/16\rfloor+(k\bmod 16)$。在正确索引下，参考的配对正是该 checkpoint 最自信的字节（偏移 16 处平均概率 0.3052，偏移 1 处 0.0804），方案是因果的（扰动未来字节时 $\max|\Delta\log p|=0$，扰动过去字节时 9.44），且编码器确实输出了这些字节。 |
| 由该探针导出的全部数字：13.12、13.1233、14.1804、15.7844 bits/byte 及 197.31 % | **作废** | 同一原因。 |
| 音频无法复现论文结果 | **撤回** | 它可以复现，见 §7.3。"无法复现"是上述索引错误的假象。 |
| 参考实现无法运行：缺少 `samplings` 模块，且 620 字节尾块使其崩溃 | **撤回** | `samplings` 是普通的 PyPI 包（作者 Sander Wood），且**已安装在 capsule 的 virtualenv 中**；它本就不应被 vendored 进源码树，而我们的搜索**排除了 `.venv`**。未修改的脚本跑完全部十一个块并报告 `Total size: 82264`。我们还曾运行过导入检查、看到它成功、却把成功解释掉而不是去追它。 |
| 图像"真正无损率"67.43 %，分子 330 字节 | **撤回** | 由我们自建的整图实验产生，非官方 patch-wise 路径。 |
| 基数论证（24 bit/像素 → 9 bit/token）证明图像路径有损 | **撤回** | 定义域是 256、值域是 512，基数什么都证明不了。已替换为 §8.3 的穷举，后者确实判定该问题。 |
| 以"20 bit 高于字节字母表的 8 bits/byte 上限"作为编码器最小宽度的理由 | **撤回** | 256 个符号不限制真字节的 surprisal。正确理由是报告率从不取自编码器量化后的概率。 |

## 11.1 音频撤回的细节

最大的一次撤回是音频错位声明。其根源是第九章推导的行索引错误：我们的探针使用了
扁平索引 $16+k$，而正确索引由该章的公式给出。在错误索引下，参考的配对看起来偏移了
一个 patch；在正确索引下，它是该 checkpoint 最自信的配对，且方案是因果的。
实际后果是：音频模态非但没有复现失败，反而在一次独立实现的同一管线上、
在**实际字节流**上吻合到 **0.6 %** 以内。

## 11.2 共同根源

八项撤回中有四项是同一模式：**我们寻找一个产物、在错误的地方寻找、然后把证据的缺失
当作证据**。`samplings` 一例排除了 `.venv`；音频一例把 17 slot 的行网格当作 16 slot
来索引；图像一例使用了我们自己搭的管线而非被审计的管线。

由此得到的实践教训——并塑造了本项目其余部分——是：**关于他人代码的断言，应尽可能通过
运行它来建立**；而自动检查捕获这类错误远比反复阅读可靠。第四章的两个门禁正为此存在，
且审阅 harness 的第一版直到把行索引算术显式化之后才捕获音频错误。

# 第十二章 效度威胁

**样本量。** 每种模态都在小样本上测量：三个文本文件、一个音频片段、一张图像、一个
视频片段。论文的评测使用约 100 MB 文本、256 MB 语音、197 张图像与 11 个视频片段。
因此绝对率在千分之一百分点这一层级上不可比，小于样本间方差的效应无法分辨。
文本结果 $n=3$，无误差棒。

**上下文长度。** 我们的文本运行使用上下文 4096，论文头条使用 8192。论文自己的
SI Table 9 显示这一点影响约 **0.3 pp**，与第十章所测效应同量级。本报告中任何文本比较
都受该混淆项约束，它是最重要的待做实验。

**图像分布。** 图像基线比较不是同类可比（我们的 PNG 压缩到 84.4 %，论文为 47.1 %），
因此图像基线的**量级**应被忽略，只有顺序有信息量。这**不影响**非单射结论，因为那是
处理器的性质，与图像无关。

**视频片段。** 我们的片段不是论文十一个片段之一，因此紧密的基线一致有幸运成分。
这同样不影响 iGPT 的账目结论，因为它也与片段无关。

**环境。** 文本结果产自一台 4 bit 量化路径无法工作的工作站：已安装的 `bitsandbytes`
没有 CUDA 二进制，而已安装的 `accelerate` 版本低于已安装的 `transformers` 对量化载入
所要求的版本。项目中有若干文档把文本运行描述为"4 bit NF4"；**该描述不正确，在此更正**。
结果早于这些包的安装，因此不可能使用它们；且两个文本臂使用同一 loader，故描述错误
不可能制造 LoRA 惩罚。尽管如此，在进一步文本测量前应重新确认并记录**实际 dtype**，
且每行结果都应记录 dtype 与峰值显存。

**单一作者验证。** 本复现由一人执行。三个错误被捕获，但没有理由认为已穷尽。
所采取的缓解是外部的：一份为对抗性第三方运行而设计的审阅指南与自动 harness。

# 第十四章 设计实验及其可行性

## 14.1 配对上下文实验

**问题。** 实测的 +0.312 pp 惩罚中，多少归因于适配器，多少归因于更短的上下文？

**设计。** 在 {基座, +LoRA} × {4096, 8192} 上的 $2\times2$ 析因设计，使用同样的三个
MeDAL 文件，适配器以**未合并**方式评测，基座按论文的 8 bit 配置载入。主要结果是压缩率；
关心的量是交互项 $\Delta_{8192} - \Delta_{4096}$，它把适配器效应与上下文效应分离。

**为什么必须不合并。** 第十章显示合并在未量化基座上贡献了实测惩罚的 2.84 %，且在某些
输入上会把适配器完全舍入掉。未合并评测消除了这一问题。

**决策规则。** 若交互项相对适配器主效应很小，则惩罚归因于适配器，论文 0.2 % 的增益
无法用发布的 checkpoint 复现。若交互项与惩罚相当，则该效应是上下文长度假象，
论文方向在论文自己的设置下仍可能成立。两种结果都有信息量；当前证据支持前者，
但尚未确立。

## 14.2 论文省略的训练量消融

论文报告文本微调用 10 个 epoch，而其发布的 checkpoint 显示评测损失从第 1020 步起上升。
论文没有报告任何训练量消融。在 $\{1,2,5,10\}$ 个 epoch 上扫描，并在微调确实有效的域上
进行，可以判定 MeDAL 的零结果是否为训练量效应。

合适的域是 Pile of Law 的 `eurlex` 划分，那里已发表的增益是相对 16 %
（5.86 → 4.90）而非 0.2 %。若率随 epoch 单调下降，支持训练量解释；若在约两个 epoch 处
出现最小值随后回升，则确认第十章测得的过度训练机制。同一次运行应按 epoch 存
checkpoint，这样一个训练任务即可读出整个消融。

## 14.3 替代预测器与分词器混淆项

适配断言不必用 8B 模型上的 LoRA 来检验。两个更小的选择值得规定，因为它们便宜且
控制不同变量。

| 模型 | 参数 | 本地可行性 | 控制什么 |
|---|---|---|---|
| GPT-2 | 124 M | 可行：约 2 GB，64 MB 上约 0.5–1 h/epoch | 任何因果 LM 是否适应该域；最便宜的有意义对照 |
| ByT5-base | 582 M | 紧张：约 7 GB，需要短上下文 | 字节级运行，完全消除分词器混淆；其解码器可因果使用 |
| Llama-3-8B ± LoRA | 8 B | 不可行：4 bit 路径当前在本地无法工作 | 论文配置本身 |

**两点提醒。** 第一，**掩码语言模型不适合**该比较：方法需要**因果**下一 token 分布，
而 BERT 式目标不提供它。ByT5 与 GPT-2 合适，BERT 不合适。
第二，换模型会改变分词器，因此跨模型的率比较混合了两种效应。干净的框架是固定语料、
报告**bits per source byte**——一个与分词器无关的单位，本报告通篇已在用它。

**瓶颈是时间而非显存。** 64 MB 语料约为 1 600 万 token。按十亿级参数模型实测的本地
吞吐，单个 epoch 以"天"计，这就是为什么任何忠实的微调复现都应在租用加速器上进行，
无论选哪个模型。

## 14.4 补上图像与视频的分布缺口

§7.4 的图像基线比较不是分布匹配的：我们那张航拍细节图在 PNG 下压缩到 84.4 %，
而论文为 47.1 %。在 CLIC2019 Professional 与 ILSVRC 上重跑基线可使量级可比。
注意这只影响基线的量级：第八章的非单射结论是处理器的性质，与使用哪张图像无关；
分母口径同样与图像无关。

# 第十五章 独立审阅协议

由于本复现对一份已发表的评测提出了批评性主张，且其自身有三项结论在研究过程中被推翻，
项目采用了明确的对抗性审阅协议。本章记录它，既作为方法记录，也作为同类工作的模板。

## 15.1 为什么需要对抗性审阅而非自查

本项目反复表现出的失败模式不是推理错误，而是**关于"证据在哪里"的未加检验的假设**：
一次排除了 virtualenv 的依赖搜索、一次假设行网格为 16 slot 而实为 17 的索引推导、
一次把自建管线误当作被审计管线。每一例中，假设**下游**的推理都是正确的，
重读它不会揭示任何问题。揭示错误的是**运行某种能够反驳它的东西**。

## 15.2 审阅指南

`docs/REVIEW_GUIDE_FOR_AGENT.md` 面向一位自主审阅者，其指令是**证伪而非同意**。
它包含：

1. **基本规则。** 告知审阅者存在两个代码库——作者的参考实现与我们的净室端口——
   且**第一个中的缺陷是发现，第二个中的缺陷是 bug**；两者都被明确声明可能出错。
2. **声明表**，含置信度与严重度，被撤回的声明标为已撤回。
3. **明确的"不主张什么"一节**，使审阅者能判断报告的语气是否与证据相符。其中声明
   我们不主张伪造、不主张音频头条数字有错、不主张图像或视频分母算错、
   也不主张这些模型无能。
4. **逐条验证与证伪指令。** 每条声明都配有重新推导它的命令，以及明确说明什么结果
   会摧毁它。
5. **强制的汇报格式**，要求审阅者对每条声明给出最强反论与残余不确定性，
   而非仅仅同意或不同意。
6. **一节列出什么能推翻每条结论**，依据是"无法被推翻的断言不是发现"这一原则。

## 15.3 可执行门禁

两个脚本把协议变成可运行的东西而非仅可阅读的东西。

**`tools/review_harness.py`** 覆盖十项检查：文本对齐守卫、已撤回的音频声明
（作为对**文档**而非代码的回归守卫）、图像非单射、loader 损失、参考日志过期、
LoRA 比较、`bits2bytes` 的不存在、编码器守卫、报告率口径、以及视频基线。
设计规则：每项检查打印它测到的原始量而非只给结论；抛异常的检查报告为失败而非静默跳过；
且只在期望本身就是断言之处才写明期望值。

**`tools/check_doc_consistency.py`** 把 canonical facts 编码一次，扫描全部项目文档中
位于标注撤回之外的旧值，以及已缺失的必要值。其退出码充当提交门禁。它的存在是因为
本项目的主导错误模式是**跨文档残留**：一个数字在一处被更正而另一处仍在断言旧值，
而人工重读并不能可靠地捕获它。

## 15.4 保留撤回记录

每一项被撤回的声明都保留在本报告与项目的审计产物中，并附其根源。理由不是感性的。
第一，看不到什么被撤回的读者，无法判断存留声明承载多少分量。第二，若干撤回记录的
是错误的模式，而读者很可能共享它们——尤其是把缺失的产物归因于产物本身不存在的倾向。
第三，这些撤回本身就是关于"未经审阅的自我验证之局限"的证据，而这正是本项目的一项发现。

## 15.5 协议的局限

本项目的审阅者是单个自动化 agent，而审阅指南由与声明相同的作者撰写。这两个事实都
限制了该协议所能确立的东西。一个与作者共享先验的对抗性审阅者，可能无法质疑同样的
假设；被工具捕获的两个错误之所以被捕获，是因为工具把算术独立于文字编码了下来，
而不是因为审阅者不同意。真正独立的审阅——由未编写该 harness 的人进行——仍然欠缺，
并建议在这些发现提交发表之前补上。

# 第十六章 讨论

## 16.1 什么复现了，以及为什么重要

复现在方法确如其声称之处取得成功：一个大型自回归模型向算术编码器提供条件分布。
文本复现到 0.04 pp，音频与同一管线的独立实现在**实际字节流**上吻合到 0.6 % 以内。

同样重要的是，四种模态的经典基线全部复现，且在视频上几乎精确复现
（FFV1 40.167 对 40.16；zstd 51.035 对 51.04）。基线不是论文的重点，
但它们是使其余每一行可解释的**对照**：它们确立测量器械、分母与文件处理是正确的，
从而使模型行中的分歧可归因于模型路径。

## 16.2 两种失效模式不同，不应混为一谈

把本复现概括为"论文的数字复现不出来"既容易又错误。失效有各自不同的原因：

- **图像与视频**失效于**预处理**：一个固定的、非单射的颜色量化器把源映射进 token 网格，
  而报告的率把该网格的码长与源样本数相比。分母是对的；**对象不同**。
- **文本微调**失效于**产物选择**：发布的适配器是一个训练过度的 checkpoint，
  而论文按其描述的配方正是会产生它。

两者都不是底层思想的失效。该思想是"领域理解更好的模型产生更短的码"，
而在文本基座模型与音频上，我们测到的正是这一点。

## 16.3 对评测基于模型的压缩的启示

本次审计给出一个普遍教训。当一个压缩器报告的率用某个分母去除码长时，
**分母必须与码长描述的是同一个对象**。在图像与视频路径上它并不是，
而由于两个数字各自内部自洽，算术本身不会暴露这一差异。
方法部分里的一句话——"分母是编码器实际编码的样本数"——本可以让该问题显形。

第二个教训关于论文的技术前提。其逐通道论证建立在"iGPT 的 token 是灰度值"之上，
而这对 checkpoint 用三行代码即可核查，且为假。**若 token 真的是灰度值，该论证本来
是成立的。** 这是一个小而可验证的事实前提承载了一个重大架构决策的案例。

## 16.4 能证伪自己结论的工具的价值

本项目最具可迁移性的成果可能是负面的：我们自己的三项结论是错的，
而被捕获的那些是被**专门构建的工具**（或由审阅者质疑**解释**而非数字）捕获的。
因此我们建议：任何此类复现所报告的数字都应附带能重新推导它们的可执行检查，
且撤回记录应保留在案而非被编辑掉。

# 第十七章 结论与后续工作

## 17.1 结论

1. LMCompress 管线可以从零重新实现，并复现已发表的文本结果到 **0.04 个百分点**以内，
   以及复现已发表的音频结果：我们的编码器与作者的编码器在同一载荷上相差 **0.6 %**。
2. 四类经典基线全部复现。视频是最紧的一致性（最大偏差 1.17 pp，FFV1 与 zstd 在
   0.01 pp 以内），这验证了 harness 并使模型行的解释获得许可。
3. 图像与视频的模型率**不是源数据的率**。官方预处理把每幅图像归约为 32×32、512 色的
   token 网格，而分母统计全分辨率源样本数（$5733 \times 1024 = 5\,870\,592$）。
4. 该预处理**不是单射**：256 个可能的 8 bit 通道值只映射到 **48** 个 token id，
   存在 **585** 个碰撞值对。由于编码器只发出 token id 且无边信息，源无法被恢复，
   这与论文"合并三个通道即可重建原始图像"的表述矛盾。论文给出的前提——
   iGPT 的 token 是灰度值——为假：512 个调色板条目中**没有一个是灰度**。
5. 已发表的微调结论**在方向上无法复现**。作者自己未修改的脚本测得发布的适配器使
   MeDAL 压缩在上下文 8192 下变差 **0.5901 pp**；我们的端口在上下文 4096 下测得
   变差 **0.312 pp**。发布的适配器是训练过度的第 5120 步 checkpoint，
   已越过其评测最小值八个 epoch。

## 17.2 后续工作

1. **上下文长度对照。** 在论文的 8 bit 基座上以上下文 8192 重跑两个文本臂，
   以分离适配器效应与上下文效应。这是最重要的未完成实验。
2. **训练量消融。** 论文从未消融其自身训练预算。在微调确实有效的域
   （Pile of Law，相对 16 pp）上扫描 epoch $\{1,2,5,10\}$，
   可以判定 MeDAL 的零结果是否为训练量效应。
3. **替代预测器。** 微调问题可以不用 LoRA 来问。在同一语料上微调一个更小的因果模型
   （GPT-2，124 M）在本地可行，可为适配断言提供对照；也可用字节级编解码器（ByT5）
   消除分词器混淆。注意掩码语言模型不适合。
4. **分布匹配的图像与视频评测。** 在 CLIC2019/ILSVRC 上重跑图像基线，
   在论文使用的 Xiph.org 片段上重跑视频基线，使量级可比。
5. **构造即无损的变体。** 图像路径的自然修法是对源与量化重建之间的残差编码。
   我们测得的精确重建补全在视频帧上为 RGB 字节的 73 %、在静图上也是 73 %，
   比所有被测经典编解码器都差——这是一个有用的界，说明表观优势来自**代理对象**
   而非残差。
