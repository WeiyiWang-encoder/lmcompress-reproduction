## 1. 复现方法：为什么是"自己的代码"

要求是用自己的代码复现而非提交源代码，所以没有调用原 capsule 的任何压缩逻辑，
只把 **bGPT 的模型结构定义** import 进来以保证权重能装进结构相同的模块图；其余全部重写：

| 模块 | 作用 |
|---|---|
| `src/uic/coder.py` | **自研算术编码器**（整数区间、base-2、32 bit） |
| `src/uic/engine.py` | 可断点续跑测量驱动、原子写盘 |
| `src/uic/models.py` | bGPT / ImageGPT / Llama 三个预测器 + 对齐推导 |
| `src/uic/data.py` | 文本/音频/图像/视频四种模态加载 |
| `src/uic/y4m.py` | 自带 YUV4MPEG2 解析器（不依赖 ffmpeg） |
| `src/uic/runner.py` | 窗口规划、批次执行、聚合 |
| `tools/*` | 基线测量（Python + WSL 下运行论文原版 Linux 二进制）、audit 探针 |

**断电保护**：每个 forward pass 结束后原子写盘进度（`ChunkCursor`），
断电最多重算一个窗口；结果按单元追加 JSONL；重跑同一命令自动跳过已完成部分。

## 2. 发现并修复的三个真问题

### 2.1 自研算术编码器的区间塌陷（我自己的 bug，已修）

区间编码按 `low + width * cdf_lo // FULL` 细分。若某符号被量化到宽度 1，
而当前 `width < FULL`，则 `width * cdf_hi // FULL == 0`，`high` 会跌到 `low` 以下，
**静默产生解码为错误符号的码流**。触发它的符号真实概率是 `9.06e-11`。
修法是给每个符号保留最小宽度（`FULL >> 20`），并在编码器里加断言。

**一处措辞更正**（审阅指出，已采纳）：早期版本称该保留"因 20 bits 高于 byte alphabet 的
8 bits 上限所以不会影响报告的 ratio"。**这不成立**——256 个符号并不限制真字节的 surprisal，
模型给出 `p < 2^-20` 时 floor 确实改变了 coder 使用的分布。
正确理由是：**报告的码率根本不消费 coder 量化后的概率**，它是模型 float32 概率上的
`Σ -log₂ q(true symbol)`；量化后的 cdf 只影响 arithmetic-coded 码流长度，后者单独统计。

**关于参考实现**：我们只指出**结构性风险**（它的 `normalize_pdf_for_arithmetic_coding`
加 epsilon 再归一化，同样留有这个失效模式的可能），**并未构造出让其 coder 实际失败的输入**。
这是风险提示，不是已证实的缺陷。

### 2.2 文本模态跑不起来的真实原因

代码里**根本没有 `bits2bytes` 这个符号**（全仓库检索无果）。真实原因有两个：

1. `AutoModelForCausalLM.from_pretrained(model_path)` **没有传 `torch_dtype`**，
   等于以 **float32 加载 8B 模型（约 32 GB）** 再 `.to("cuda")` → 12 GB 显卡必然 OOM/崩溃。
   本复现用 4-bit NF4 加载只要 **5.71 GB / 18 秒**。
2. 未定义的名字是 `compression_utils`（出现在 `encoder_decoder()` 里），
   而该函数在 `compress_with_llm()` 中是被**注释掉**的。

### 2.3 bGPT 的 patch/字节对齐（差一格就毁掉压缩率）

`bGPTLMHeadModel.forward` 会把 `masks[:,0]` 置零并左移掩码，**返回的 logits 从 patch 1 开始**，
每个 patch 给出 17 个 slot 预测。展平后 payload 第 `i` 个字节位于**扁平索引 `i + 16`**
（第 17 个 slot 承载下一个 patch 首字节的预测，不能丢）。原实现固定砍掉 16 行前缀**并**砍掉每行
最后一格，于是它实际评分的网格位置是 **1…8160**，而 payload 位于 **16…8175**：
开头 15 与结尾 15 字节从未被评分，且每个分布都配到了相隔一个 patch 的目标。

> **(a) 原始 Llama-3-8B** 与 **(b) 论文作者随 Code Ocean capsule 发布的 LoRA 适配器**
> （`data/model/finetuned_llama/Llama-3-8B_lora/`）。
> 该适配器是**作者自己微调的产物，不是本次复现训练的**，也不是外部提供的。
> 证据：它的 `adapter_config.json` 记录的 `base_model_name_or_path` 是作者机器上的路径
> `<a path on the authors' machine>`；同目录还留有作者 8 路 pipeline
> 训练的 DeepSpeed 优化器分片（`bf16_zero_pp_rank_0..7_*_optim_states.pt`）。
> 因此本节的对比回答的是"**作者发布的微调适配器是否优于基座模型**"，
> 而**不是**"我们自己微调的效果如何"——后者是 §6.5 / Colab Part B–C 的任务。

**设置**：Llama-3-8B ± **作者发布的 LoRA 适配器**；4-bit NF4（论文用 8-bit）；

两臂使用**完全相同的窗口切分与代码路径**，唯一差别是是否挂载 LoRA；
全部 57 547 tokens 已正确计入（`coded_symbols == symbols`）。

**结论**：

1. **模型数值复现**——原始模型（对应论文 LMCompress\*）差 **0.04 pp**，基本逐位吻合。

### 3.1 发现并修复的对齐缺陷（这些数字的来源）

早期版本存在**目标切片晚一位**的缺陷：

```python
scope   = logits[:, offset     : offset + n_target, :]
targets = ids[   :, offset + 1 : offset + 1 + n_target]   # ← 晚一位
```

由于位置 `p` 预测 token `p+1`，token `offset+1` 的预测在 `logits[offset]`，
于是**每个 token 都在用"前一个 token"的分布打分**；一个"丢掉第一个预测"的补偿
既掩盖了错误，又静默丢弃每个文档的最后一个 token。它是被审阅者质疑那句错误解释
（"causal model 无法预测最后一个 token"——这是**错的**，causal LM 由倒数第二个位置正常预测它）
时才被查出来的。

现已修正：被打分区间**前后各带一个 context token**（前驱与后继），二者都不计分；
并且 `iter_steps` 现在**逐 token 断言**目标必须等于文档中对应的 token，任何位数的滞后都会立即报错。
修复前数值为 9.0333% / 9.3459%；修复后两臂都略微变大，且**原始模型更贴近论文**。

### 4.1 order-1 熵的对比 —— 只是旁证，不是证明

### 4.2.2 文本基线：补齐论文的固定窗口协议

原来这一节只报了整文件压缩，然后以"协议不同所以不比较"收尾。**那是错的** ——
协议本身很便宜就能复现（`tools/baselines_text_windowed.py`，纯 CPU、几秒），所以现在补上了。
做法：把文件切成 8192 / 16384 / 32768 字节的连续块，**每块用全新的压缩器状态**独立压缩，
另外整文件压缩一次作为"无界"列。

| 编码器 | 8192 | 16384 | 32768 | 无界 |
|---|---|---|---|---|
| brotli q11 | 31.84 | 30.91 | 30.17 | 28.81 |
| lzma 9e（7z 等价） | **41.44** | **38.40** | **35.78** | **31.68** |
| zlib 9 | 41.78 | 39.67 | 37.70 | 35.02 |
| zstd -22 | **40.38** | 37.93 | 35.69 | 31.99 |

对照论文 SI Table 11：

| 编码器 | 窗口 | 我们 | 论文 | 差 |
|---|---|---|---|---|
| 7z | 8192 | 41.44 | 42.02 | **−0.58** |
| 7z | 16384 | 38.40 | 38.21 | **+0.19** |
| 7z | 32768 | 35.78 | 35.26 | **+0.52** |
| 7z | 无界 | 31.68 | 23.89 | +7.79 |
| zstd | 8192 | 40.38 | 39.54 | **+0.84** |

**7z 的四列里有三列吻合到 0.6 pp 以内** —— 这是对论文基线网格的**真正复现**，
比原来那句"不比较"强得多。

**无界列是例外，原因已知**：论文用了约 180 MB，我们只有 313 KB。没有窗口限制时，
压缩器从更多输入中直接获益；我们自己的表也显示了同样的梯度（7z 从 41.44 降到 31.68 %）。
所以 +7.79 pp 是**语料规模效应**，不是协议错误。

**对模型比较的后果**：现在有了同口径比较，而且这才是该引用的那个数 ——
我们的模型在 8192 字符窗口下 **6.3321 %**，我们的基线在 8192 字节窗口下最好的是
brotli **31.84 %**，倍数 **5.0×**；论文自己的对照是 9.06 % 对 zstd 39.54 %，倍数 **4.4×**。
**模型相对经典压缩的优势在同窗口下也复现了。**

### 4.3 最终结果：音频模态复现成功

样本 `LJ001-0004.wav`，16 kHz 单声道 8-bit PCM，**82 220 字节**，以下数字均覆盖全部字节。

| 实现 | 编码输出 | bits/byte | **rate**（压缩后/原始） | ratio |
|---|---|---|---|---|
| **我们的端口** | 130 383 bit = 16 298 B | 1.5858 | **19.82 %** | 5.046× |
| **参考实现（未修改脚本）** | 16 399.95 B | 1.5957 | **19.94 %** | 5.016× |
| 论文 headline（LJSpeech） | — | 1.4608 | **18.26 %** | 5.477× |

我们算术编码器**真实吐出的码流**为 1.5858 bits/byte，参考实现报告 1.5957，**相差 0.6 %**。
按 `Σ −log₂ q` 口径为 1.6641 bits/byte（20.80 %），比参考高 4.29 %——两者之差是编码器
量化开销，代码中分别记为 `coded_bits` 与 `ac_bits`。

**音频模态复现成功。** 参考实现与论文 18.26 % 的相对差为 **9.2 %**，与本文档其他模态的
经典基线偏差同一量级（音频基线 OptimFROG +1.89 pp、WavPack +2.15 pp、FLAC +4.07 pp），
且顺序不变：**模型明显优于所有经典编码器**（19.8 % vs OptimFROG 27.3 %）。

> **三次错误记录（防止重犯）**
>
> **1. 「打分错位 16 位」——已撤回。** 我们的探针把扁平 logits 索引写成 `16 + k`，
> 但一行 patch 有 **17** 个 slot 预测，位置 k 的正确行号是 `17*(k//16) + (k%16)`。
> 按正确映射实测：参考实现的配对正是该 checkpoint 最自信的字节（偏移 16 处平均概率
> **0.3052**，偏移 1 处仅 **0.0804**），方案**是因果的**（扰动目标之后字节
> `max|Δ log-prob| = 0`；扰动之前字节变化 **9.44**），编码器确实输出了这些字节。
> **由该探针导出的 13.12 / 13.1233 / 14.1804 / 15.7844 bits/byte 及 197.31 % 一律作废。**
>
> **2. 「尾块导致脚本崩溃」——已撤回。** `split(..., 8160)` 确实给出 10 个完整窗口加一个
> **620 字节**尾块，`byte_collate` 也确实把它补成 **652** 字节（不能被 16 整除）。
> 但**未修改的脚本跑完了全部 11 个块**并报告 `Total size: 82264`——预测的崩溃没有发生。
>
> **3. 「`samplings` 阻断运行」——成立，已解决。** capsule 确实不含 `samplings.py`，
> 而 `data/model/bgpt/utils.py:9` 顶层 import 它，故任何入口都在导入阶段失败
> （`tools/verify_reference_blockers.py` 已核实文件不存在）。重建模块见
> `replacement_modules/samplings.py`；这三个函数只被自定义 `generate`（第 178–180 行）
> 使用，**从不被 `forward` 调用**，因此不可能影响压缩测量。
> `tools/run_reference_audio_onewindow.sh` 把 capsule 复制到临时目录、装入该模块后以
> **未修改**的脚本运行——**原 capsule 始终未被改动**。

**复现步骤**：`tools/confirm_tail_and_our_window.sh`。原始输出见
`results/_tail_and_window.txt` 与 `results/_refrun_onewindow.txt`。

### 5.2 官方图像路径的实测结果：它**不是**对源图像的无损压缩

我们**直接驱动官方代码**（`compress_with_igpt.py` → `language_model.compress`），
并在**类级别**给 processor 打桩（实例级打桩会静默失败，因为 `_retrieve_model_params`
会重新 `from_pretrained`）。实测到的形状链：

```
官方 loader chunk:  shape=(32, 32, 1)   pixels=1024      ← 逐通道 32×32 patch
官方 coder 输出:    165 bytes（单 patch）
processor 调用:     1 次, input=(32,32,3) -> tokens=(1,1024)
processor 配置:     do_resize=True, size=32×32, do_color_quantize=True, 512 clusters
官方分母:          h*w = 1024（patch 面积），不是原图像素
```

**完整账目**（生成器耗尽后；`tools/probe_official_image_accounting.py`。
注意官方日志只每 100 个 chunk 打印一次，**它自己日志里的总数是被截断的**）：

| 量 | 值 |
|---|---|
| chunks | **5 733** |
| processed samples (`raw_length`) | **5 870 592** |
| 码长 | **910 788 字节** |
| **rate** | **15.5144 %**（ratio 6.4456×） |
| 源 RGB channel samples | 5 872 164 |
| 被 loader floor division 丢弃 | **1 572**（每通道 524） |
| 论文（CLIC2019） | 14.62 % |

**为什么它不是无损的——用穷举证明，而不是基数论证。**
官方路径先逐通道切开，所以 `language_model.compress` 拿到的是 `(32,32,1)`，
再 `np.repeat(...,3,axis=2)`。**每个 processor 输入都是由一个 8-bit 通道值构成的 `(v,v,v)`**，
域是 256、值域是 512 —— **512 > 256，基数论证什么都证明不了**（审阅者正确地指出了这一点）。
唯一的严格办法是穷举整个域（`tools/test_igpt_injectivity.py`）：

| 量 | 值 |
|---|---|
| 域大小（灰度值） | 256 |
| **像大小（不同 token id）** | **48** |
| 单射 | **False** |
| 碰撞值对 | **585** |
| 最大碰撞类 | token 391 ← **7 个值**（78…84） |

```
token  71  <-  灰度值 [0, 1, 2, 3]
token  59  <-  灰度值 [8, 9, 10, 11]
token 391  <-  灰度值 [78, ..., 84]
```

**真实 patch 上同样碰撞**（不是合成常量输入的假象）：patch #116 有 110 个不同源值 →
32 个 token，29 个 token id 接收多个源值（如 token 143 ← [35,36,37,38,39]）。

**结论**：存在 `a ≠ b` 使 `token(a,a,a) == token(b,b,b)`；coder 只发这个 id、
无 residual 或任何 side information，**因此不存在能从该码流唯一恢复源值的 decoder**。
即**对 token 流无损，对图像有损**。这里分母是**自洽的**（它数的是实际被处理的样本），
所以这是一个**tokenisation 缺陷**，不是 denominator mismatch。

**关于 15.51% vs 14.62%**：这是**数值上接近、同一量级**，说明官方 **accounting 口径**
足以解释论文数字的量级——但它**不是** dataset 层面的复现（这张图是航拍细节图，不是 CLIC）。
§5.1 已显示同一张图在经典基线下与 CLIC 差异巨大。

> **已撤回内容**：早期版本报告 330 字节 / 0.017% / 67.43% "真正无损率"，
> 来自**我们自己的 whole-image 实验**（整图 → 单个 32×32 token grid），
> 既不是官方路径，分母也用错了。该节已整体撤回，**不是 C7 的证据**。
> 见 `docs/AUDIT_FOR_REVIEW.md` §4.4.3。

而下面经典编码器可以利用时间冗余。

| 量 | 值 |
|---|---|
| 去重后帧数 | **9**（10 行中 2 行相同，见下） |

**同一批帧上的经典基线**

| 编码器 | 我们 (%) | 论文 (%) | 差 |
|---|---|---|---|
| H.265 crf 0 (x265 veryslow) | **26.467** | 21.69 | +4.78 |
| H.264 crf 0 (x264 veryslow) | **34.087** | 37.42 | −3.33 |
| FFV1 level 3 | **40.114** | 40.16 | **−0.05** |

两个要点。第一，**顺序完全复现**（H.265 < H.264 < FFV1 < zstd）—— 这是"装置在测论文所测之物"的检验。
第二，**模型优于最好编码器 1.46 倍**（18.15 % vs 26.47 %），这是论文对视频的核心定性主张，

（H.265 +4.78，zstd −4.75），所以"片段间差异可达数个百分点"已由我们自己的对照确立。
我们本地那份不同的航拍片段首帧测得 **16.7162 %**，比这份更接近论文值 1.4 pp。
**诚实的解读是：模型落在论文量级内，残差主要由片段决定，而 10 帧单片段无法再分辨。**

**已作废的数字**：此前的 **0.0042 %** 与精确补全 **73.05 %** 来自整帧 RGB token 化
（缺陷记录在 `AUDIT_FOR_REVIEW.md` §4.4.4），与更正后的值差三个数量级，已作废。

**输出里的两个缺陷，都已记录而非掩盖**

1. **重复行**：写了 10 行，但只有 **9 个不同的 `coded_bits`** —— `frame_000000` 与 `frame_000001` 逐位相同（都是 38 532 200.173828），即一帧被算了两次（很可能跨会话重启）。去重后 **18.1512 %**，比输出的 18.1508 % 差 0.0004 pp，**不影响任何结论**，但正确帧数是 **9** 而非 10。
2. **列标签错误**：每行记录的是**汇总后**的 `coded_bytes`
而不是该帧自己的字节数，所以十行的该列看起来相同，而 `coded_bits` 是不同的。
**所有 rate 都由 `coded_bits` 算出，均正确**；只有那一列冗余字段是错的。
已在 notebook 修正并记录于此，避免读者误以为帧被重复计算。

### 5.9 文本量级差到底是什么性质：四选一的分析

我在前面把论文的文本数说成"偏悲观"，这个说法太含糊。你的追问是对的 ——
需要区分是**口径**、**计算**还是**代码**。下面把形容词替换成四个候选机制，并用测量排掉三个。

| # | 候选 | 含义 |
|---|---|---|
| A | **口径** | 计什么不同：分母、哪个分布编哪个 token、窗口边缘排除什么 |
| B | **计算** | 同一口径用不同表达式（该用和却用了均值、对数底、掩码位置） |
| C | **代码** | 某条路径的实现缺陷 |
| D | **语料** | MeDAL 的不同子集，本身压缩率就不同 |

#### A（口径）在位移上被排除

参考实现的 `forward_next` 用的是

```python
shifted_logits     = logits[:, :-1, :]
shifted_input_ids  = input_ids[:, 1:]
```

即位置 *j* 打分 token *j+1*，这是**正确的因果对齐**。而独立 gather 复现模型自身 loss：
算出 `10516.775` bits，`output.loss*(L-1)` 为 `10516.776`，相对差 **5.6e-08**。
**两侧都没有位移错误。**

#### A（口径）在分母上被排除

容器 vs 抽出载荷差 **0.39 %**（313 272 vs 312 053 字节）；载荷字符 vs 载荷字节差 **0.14 %**。
2.73 pp 的差距不可能来自这两个。

#### D（语料）被实测排除

`tools/test_corpus_subset.py` 在论文的 8192 字节窗口下，对样本里**全部 100 个** CSV 跑了 brotli 与 lzma：

| 编码器, 窗口 | 全库最小 | 全库均值 | 全库最大 | 我们三个 | 我们均值 |
|---|---|---|---|---|---|
| brotli, 8192 | 30.26 | 31.53 | 32.99 | 31.73 / 31.77 / 32.01 | **31.84** |
| brotli, 无界 | 26.96 | 28.47 | 29.56 | 28.61 / 28.78 / 29.02 | **28.80** |
| lzma, 8192 | 38.72 | 40.68 | 42.40 | 41.09 / 41.36 / 41.86 | **41.44** |
| lzma, 无界 | 29.55 | 31.25 | 32.41 | 31.39 / 31.51 / 32.15 | **31.68** |

**整个语料库对经典压缩器只跨 2.7 pp**，而我们的三个文件比全库均值**更难压** 0.31–0.76 pp。
更难压的子集会让模型码率**上升**，而要解释的差距是我们**低于**论文。
**所以语料选择不能解释这 2.73 pp。**

#### 剩下 B 与 C，而且可以把范围收窄

参考 harness（**8.9253 %**）与我们端口（**9.0410 %**）在**相同权重**上都报告约
**1.48 倍**于模型自身 loss 隐含的码长 —— 3.87 与 3.80 bits/token 对 **2.5682** ——
而直接前向是 1.00 倍。

**两条彼此独立编写的管线落在同一个膨胀倍数上**，这是"共享环境原因"的特征，
而不是两个不同代码库里恰好同时出现的两个 bug。而唯一能在**不改公式**的前提下
把交叉熵抬高 1.3 bits/token 的东西，就是**模型本身处于不同状态**。

因此首要候选是**精度**，不是算术：论文自述基座按 **8-bit** 加载，而本机**根本做不了 8-bit**
（bitsandbytes 无 CUDA 二进制）。一个量化后的 8B 模型在领域外的医学文本上，损失一个 bit/token 量级是合理的。
**这一个假设就能解释 1.48 倍，而不需要任何一方存在 bug。**

**在 A100 上判别它很便宜**：同一个窗口跑三种精度（bf16 / 8-bit / 4-bit），看哪个复现 3.87 bits/token。
若 8-bit 落在 3.87 附近，则差异是真实的精度效应，**论文的数与我们已撤回的端口数都是对量化模型的诚实测量**；
若 8-bit 仍在 2.6 附近，则两条管线共享一处计算缺陷，定位它就成为必须。

**在该测试完成前不能声称的**：既不能说"论文偏悲观"，也不能说"我们端口文本路径有 bug"。
可以声称的是上面的排除结论 —— 位移、分母、语料三者都由测量排除，
范围已经收窄到"精度或共享计算"。

### 5.8 【撤回】我们的文本码长偏大约 48%

**实测**（`tools/isolate_harness.py`，`medal_102285.csv` 的第一个 4096-token 窗口，
用**胶囊自己的** Llama-3-8B，CPU，bf16）：

| 量 | bits | bits/token |
|---|---|---|
| 普通 HuggingFace 前向，因果位移 | **10 516.775** | **2.5682** |
| 同一数值经 `output.loss * (L-1)` | 10 516.776 | 2.5682 |
| 相对差 | **5.6e-08** | — |
| 我们端口记录的同文件结果 | **73 410.306**（19 333 计分 token） | **3.797** |

前两者吻合到 6e-08，意味着该评分器**构造上就是对的** —— 它等于模型自己的 loss。
而权重也不成问题：胶囊权重与公开权重**逐字节相同**
（`model.norm.weight` 与 1 051 MB 的 `model.embed_tokens.weight` 两个哈希都一致）。

**所以，在相同权重上，我们端口比模型 loss 所隐含的码长多报了 48%**（3.797 / 2.5682 = 1.478）。

**撤回什么**

1. **文本 base 的 9.0410 % 是错的。** 本语料上正确的因果码长约 **6.0 %**，
   这正是配对 A100 实验测到的（4096 token 下 6.1657 %，8192 字符下 6.3321 %）。
2. **"文本 base 与论文吻合到 0.04 pp"这句话撤回。** 那是两个不同的偏大值恰好落在相近位置，
   是最没有信息量的一种"吻合"。
3. **+0.312 pp 这个具体惩罚数值被替换。** 配对实验在正确装置上测得
   **+0.3987 至 +0.4728 pp**，五个上下文全为正。定性结论保留，数字不保留。
4. **论文的 9.06–9.36 % 也不可能是该模型上的普通因果码长。** 参考实现自己的
   `forward_next` 位移是正确的（`logits[:, :-1, :]` 对 `input_ids[:, 1:]`），
   所以它在本语料上跑应当也落在 6 % 附近而不是 9 %。
   要么论文的数字来自不同语料或设置，要么此前归给"作者原始 harness"的 8.9253 % 并非我们以为的那个量。
   **本报告不猜是哪一种。**

**缺陷已定位范围但尚未定位代码。** 比值 1.478 接近 `log2(e) = 1.4427` 但并不相等，
所以**不是**简单的自然对数/log2 混用 —— 还差 2.4%，对数底错误不会产生这个残差。
本次尝试直接驱动端口的 `iter_steps` 时，它在 `self._all_tokens[doc_start + i]` 处
抛出 `IndexError`（该列表由 runner 填充），所以探针的端口臂没有跑完；
上面的比较依据的是端口的**已记录汇总值**，不是一次新的端口运行。
定位缺陷还需要再过一遍 `LlamaTokenPredictor.iter_steps`。

**这个错误为什么能活到现在**：端口与作者 harness 吻合到 0.0622 pp，两者又与论文吻合。
三方一致被当成了验证。实际上那只是**同一个约定被数了三遍** ——
正是本报告在 §4.1 已经命名过一次的失效模式。A100 那次运行是本项目第一次
**用模型自己的 loss** 而不是用"另一个同想法的实现"来做校验的测量。

### 5.7 十格配对实验：混淆项解决了，绝对量级还没解决

`results/text_paired.json`（Colab A100）在两条窗口轴上各测了双臂。

**装置校验（全部通过）**：适配器 **20 971 520** 参数、语料 **312 053** 字节、
字符窗口 **78/51/39**、token 窗口 **15/9**、dtype **bf16**、峰值显存 **20.44 GiB**（与 8B 模型相符）。

**率 (%)**

| 臂 | A: 4096 字符 | A: 6144 字符 | A: 8192 字符 | B: 4096 token | B: 8192 token |
|---|---|---|---|---|---|
| base | 6.5322 | 6.3927 | 6.3321 | 6.1657 | 6.1023 |
| +LoRA | 6.9319 | 6.7958 | 6.7308 | 6.6107 | 6.5751 |

**适配器惩罚**

| 上下文 | 惩罚 (pp) |
|---|---|
| A 4096 字符 | **+0.3997** |
| A 6144 字符 | **+0.4031** |
| A 8192 字符 | **+0.3987** |
| B 4096 token | **+0.4450** |
| B 8192 token | **+0.4728** |

**在每一个上下文下都为正，极差只有 0.0741 pp。** 同一跨度上的上下文效应最多
**0.2001 pp**（字符轴）与 **0.0634 pp**（token 轴）。

**所以混淆项解决了。** 上下文效应比惩罚**更小**，且惩罚在任何上下文下都存在。
原先"无法分离 +0.312 pp 与约 0.30 pp 上下文效应"的限定，
现在变成了一个测量结果：适配器在这里值 **0.40–0.47 pp**，上下文最多贡献 **0.20 pp**。
方向也与作者原始 harness 一致 —— 它在 8192 字符下的惩罚是 **+0.5901 pp**，比我们 4096 token 的更大而非更小。

**但出现了一个阻断绝对数字的异常。** 每一格都比三个独立来源**好 2.6–3.0 pp**：

| 测量 | 率 | 装置 |
|---|---|---|
| 本 notebook，base，A@8192 字符 | **6.3321 %** | 本次，A100，bf16 |
| 本 notebook，base，B@4096 token | **6.1657 %** | 本次 |
| 论文 SI Table 9 @8192 | 9.06 % | 已发表 |
| 作者原始 harness @8192 字符 | **8.9253 %** | 参考脚本 |
| 我们端口 @4096 token | **9.0410 %** | `uic` |

折成 bits/token：本次 **2.65–3.01**，其余三者都是 **~3.9**（困惑度 6.3–8.0 对 ~15）。
上面的校验排除了常见解释 —— 语料错、分词器错、窗口数错、模型被换小、适配器没加载、
评分器位移错（notebook 用 `output.loss` 断言，实测吻合到 1e-8）。

还剩两种可能，本报告不选边：

1. **其余三者共享同一处退化。** 论文明确说文本的基座模型按 **8-bit** 加载。若该路径差于名义值，
   或参考脚本的 CPU/RAM 路径行为不同，则论文、harness、我们端口会**一起偏悲观** —— 正是表里的形态。
2. **本次运行因某处未被校验覆盖的信息泄漏而偏乐观。** 评分器已验证，但泄漏可能在别处，
   例如窗口张量喂给模型的方式。

**判别实验很便宜且具体**：在**同一台 A100、同样 bf16、同样的 HF 权重**上跑作者原始 harness。
若它给出约 6.3 %，则可能 1 成立、本 notebook 正确；若仍是约 8.9 %，则可能 2 成立、本次运行有缺陷。
**在此之前，本报告不引用任何文本绝对码率**，正文已如此声明。

惩罚的结论不受影响：常数偏移不改变差值的符号与大小，所以**惩罚能确定地说，量级不能**。

### 5.5 两个"上下文长度"根本不是同一个量

这是在写配对 notebook 时发现的，它改变了本文所有文本数字与论文的比较方式。

**参考实现按字符切窗。** 它把语料存成字符串，然后

```python
def split(s, max_length):
    return [s[i : i + max_length] for i in range(0, len(s), max_length)]
split(self.data[0], context_window_size)      # self.data[0] 是 text_str，str
```

所以 `--context_window 8192` 是 **8192 个字符**，不是 8192 个 token。

**我们端口按 token 切窗**（`text_units` 先分词，predictor 再按 `--context-window` 切 id 列表）。
同一语料上两条轴实测：

| 设置 | 窗口单位 | 窗口数 | 平均 token/窗口 |
|---|---|---|---|
| 论文 4096 | 字符 | 78 | **739** |
| 论文 6144 | 字符 | 51 | **1129** |
| 论文 8192 | 字符 | 39 | **1476** |
| 我们 4096 | token | 15 | **3836** |
| 我们 8192 | token | 9 | **6394** |

**我们的"上下文 4096"带的上下文比论文最大设置还多 2.6 倍。**

**这个发现作废了什么、没作废什么**

* **没作废**测量本身：base 9.0410 % 与 +LoRA 9.3529 % 对"4096 token 窗口"而言是正确的。
* **作废了对论文 9.36 % 那一行的比较**。那行是 739 token 的上下文，我们是 3836，比较是无效的。
  而且误差方向可知：上下文越长压得越好，所以我们的 9.0410 % 应当**低于** 739 token 的数，事实正是如此。
* **也解释了一个本来很可疑的巧合**：我们的 9.0410 % 落在论文 8192 行（9.06 %）附近而不是 4096 行（9.36 %），
  看着像复现得很好，其实是更长的上下文恰好落到了同一个位置。
* 适配器惩罚（+0.312 pp）作为一个测量不受影响，但它与论文 LoRA 结论的可比性现在有**双重限制**：
  窗口单位不同、有效上下文也不同。

**这也重新打开了一个矛盾**：正文说文本上下文是 **1024**，而 SI Table 9 报的是 8192 / 6144 / 4096。
按字符算，1024 字符窗口只有约 190 token，压缩率会远差于 9.06 %，
所以"1024"不可能是与 Table 9 自洽的字符窗口。它要么是 token 数、要么是另一个实验、要么是笔误。
本报告不猜，但现在有了说明这个问题所需要的单位信息。

**补救**是 `colab/Text_Paired_Context_Colab.ipynb`：**两条轴都测** ——
字符窗口（4096/6144/8192，可直接对 Table 9）与 token 窗口（4096/8192，可与我们的端口对照），
并与双臂交叉，共 10 个单元格。字符轴自带独立校验：作者的原始 harness 在 8192 字符下
给出 base **8.9253 %** / +LoRA **9.5154 %**。

### 关于"为什么当初不在 8192 下测"

**两种可能的解释都不成立，而且其中一种我一开始说错了。**

| 可能的解释 | 实际情况 |
|---|---|
| "12 GB 显存只够 4096" | **这个理由不成立，但细节要分清。** 论文三档峰值显存**都是 15.49 GB（14.43 GiB）**，所以上下文长度确实不改变占用；但 15.49 GB 是 **8-bit** 的数字，而本机 **8-bit 不可用**（bitsandbytes 缺 CUDA 二进制）。bf16 下 8B 模型**仅权重就 14.96 GiB**，显存只有 **11.94 GiB** —— 不加量化**任何上下文长度都放不进**。所以显存是真限制，但它对 4096 和 8192 **一样成立**，不能用来解释两者之间的选择。 |
| "上下文越长越慢，时间预算不够" | **错，而且方向相反。** 论文自己的耗时随上下文变长而**下降**：4096 用 7323 s，6144 用 6855 s，**8192 只用 3072 s**（同一语料）。 |

实际情况是：端口写的时候把默认值定成 4096，文本双臂就用这个默认跑了；而上下文这个混淆项是在后来为了别的原因去读 Table 9 时才意识到的。

**代价是这份复现无法把"适配器效应"与"上下文效应"分开**，因此凡引用 +0.312 pp 都必须带上该限定。

**补救很便宜**：我们的三个测试文件合计只有 **57 547 tokens**，4096 下的 10 个窗口在 8192 下会变成 3 个窗口，**总 token 数不变**。成本是小时级，不是天级。

之所以记录而不是悄悄改掉，是因为读者有权知道一个混淆项究竟是"客观限制"还是"疏忽"。**这次是疏忽。**

### 6.3 那么"差在哪里"？—— 目前只能给出受限的结论

三条证据：

1. 论文自己的曲线显示最优在 ~2 epoch，继续训只会变差；
2. 论文报告 MeDAL 上的增益是 9.08 → 9.06，**相对只有 0.02 pp，本来就在噪声里**；
   而 eurlex（法律）上是 5.86 → 4.90，**相对 −16.4%**，差异巨大；
3. 同一个 LoRA 配方在两个域上效果天差地别，指向**域匹配**而非训练量。

**但是**：我测到的 +0.312 pp 惩罚与我使用的**较短上下文（4096 vs 8192）**可能造成的
约 0.3 pp 差异**同量级**（论文 Supplementary Table 9）。因此诚实的说法是：

> 在 ctx 4096、n=3 的条件下，发布的适配器没有带来增益，反而略微有害；
> **但该惩罚中来自适配器与来自上下文长度的比例尚未分离**，
> 需要 ctx 8192 的双臂对照才能定论（§7）。

至于"训练量是否是差距来源"：论文**没有做任何训练量消融**，而它自己的日志显示最优在 ~2 epoch、
之后持续变差——这与"训练量越多越好"相反。所以**至少可以否定"只需提高训练量"这一表述**，
但**不能**仅凭此断定域匹配是唯一因素，那需要 §6.5 的消融。

### 6.4 论文该怎么写（替代"只需提高训练量"）

> 域内微调的收益取决于**目标域与微调语料的匹配程度**，而非训练量。
> 在 eurlex（法律）上，64 MB 域内微调使压缩率从 5.86% 降到 4.90%（相对 −16.4%）；
> 而在 MeDAL（医学）上收益仅 0.02 pp，落入噪声。进一步地，本复现发现该 LoRA
> 的最优评测点出现在约 2 个 epoch（eval loss 2.4708），继续训练至 10 个 epoch
> 反而使评测损失上升 8.2%。因此**训练量的边际收益为负**，关键变量是域匹配与早停，
> 而非训练步数。

### 6.5 待 Colab 验证的两个实验

1. **上下文对照**（优先，因为它是当前最大的混淆项）：ctx ∈ {4096, 8192} × 双臂（±LoRA），
   分离适配器效应与上下文效应。
2. **训练量消融**：在 eurlex（增益大的域）上扫 epochs ∈ {1, 2, 5, 10}，其余保持论文配方。
   若码率随 epoch 单调下降，"数量说"成立；若在 ~2 epoch 取极小后回升，则 §6.3 得到确认。

两者已写入 `colab/LMCompress_Colab_H100.ipynb`（Part A 与 Part C），
按 epoch 存 checkpoint 并支持断点续跑。
