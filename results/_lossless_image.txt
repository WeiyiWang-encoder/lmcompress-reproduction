A) What does the iGPT path actually put into the arithmetic coder?
------------------------------------------------------------------------------
   language_model.compress, the encode call(s):
     encoder.encode(normalize_pdf_for_arithmetic_coding(pdf), symbol)
     encoder.encode(normalize_pdf_for_arithmetic_coding(pdf), symbol)
   where `symbol` comes from:
     sequence_array = data
     previous_array, sequence_array = data
     sequence_array = tokenizer(data, return_tensors='pt')['input_ids'].to(device)
     sequence_array = image_processor(sequence_array, return_tensors='pt').to(device)['input_ids']
     sequence_array = np.repeat(sequence_array, 3, axis=2)
     sequence_array = image_processor(sequence_array, return_tensors='pt').to(device)['input_ids'].to(torch.int64)
     sequence_array = sequence_array.detach().view(-1).cpu().numpy().squeeze()
     symbols.append(symbol)
     correct_symbols.append(symbol)

   `sequence_array` is the ImageGPT processor output (token ids), and the
   coder emits exactly that id -- there is no residual / side channel.
   The quantiser is non-injective (256 -> 48 ids, 585 colliding pairs),
   so no decoder can invert it.  => the image and video paths are LOSSY.
   (Text uses Llama token ids = the paper's own unit; audio uses raw bytes
    via bGPT -> those two ARE lossless by construction.)
